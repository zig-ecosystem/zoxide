## 发现并修复的真机 bug

atomic_counter 初版死锁：LLVM 将 `bar.sync` 复制到 `if (tid==0)` 条件分支两侧（extern 声明缺 convergent/noduplicate 属性），与 cuda-oxide 禁用 JumpThreading 同类。修复：条件初始化改为全线程无条件写；编码规则记入 README 已知问题。修复版本 v0.0.3-alpha 复验 PASS。

## wgmma 轮：本地已就绪，待 pod 验证（2026-09-21）

新增（宿主机仅能验证到 PTX 生成，正确性/性能待 H20 pod 跑）：

- `src/wgmma.zig`：手写 `wgmma.mma_async.sync.aligned.m64n16k16.f32.f16.f16`

  core-matrix 布局依据 CUTLASS `cute`（BSD-3-Clause）`mma_sm90_desc.hpp` /
  `mma_traits_sm90_gmma.hpp`。
- `src/examples/wgmma_smoke.zig`：自检 kernel。一个 warpgroup 填 64×16 A 与 16×16 B
  的 core-matrix packed 布局，发一条 wgmma，再按闭式重算全部 1024 个累加元素逐一比对，
  把不匹配数写回 `out[tid]`。这把最容易错的「描述符 + 布局 + 累加器寄存器映射」
  从 GEMM tiling 里隔离出来单独验。输入是小整数，f16 与 f32 都精确，不匹配即真 bug。
- `src/examples/hgemm_wgmma.zig`：64×128 block tile、单 warpgroup、K=16 分段、
  cp.async 双缓冲，每段发 8 条 `m64n16k16`。
- `build.zig` 支持按 kernel 覆盖 sm 型号（wgmma 两个 kernel 走 `sm_90a`）；
  `validateArch` 接受 `sm_90a`；`pod-verify.sh` 加 `run/wgmma_smoke` 与
  `bench/hgemm_wgmma` 两项（sm_90a 不可用时记 SKIP 而非 FAIL）。

本地已确认：两个 kernel 都能编出 `.target sm_90a` 的 PTX，指令形态为
`wgmma.mma_async.sync.aligned.m64n16k16.f32.f16.f16 {8 regs}, %rd, %rd, p, 1, 1, 0, 1`，
fence/commit_group/wait_group 位置正确，共享内存 12 KB。**尚未在 GPU 上跑过，
也没有 ptxas（宿主机 macOS 无 CUDA 工具链），所以布局正确性与性能都还是未验证状态。**

### 为什么是 n16 而不是 n128

`m64nNk16` 每线程需要 N/2 个累加器寄存器，且每个都必须是 inline asm 的 output 操作数。
Zig AstGen 把 asm output 上限硬编码在 15（`lib/std/zig/AstGen.zig`，"too many asm outputs"），
本地实测 15 个能编过、16 个报错。于是：

| shape | 累加器寄存器 | Zig 能否表达 |
| --- | --- | --- |
| `m64n16k16` | 8 | 能 |
| `m64n32k16` | 16 | 不能，正好超 1 个 |
| `m64n64k16` | 32 | 不能 |
| `m64n128k16` | 64 | 不能 |

不能靠拆分 asm 绕开——一条 wgmma 的累加器必须在同一个操作数列表里；也没有 intrinsic
可退（NVVM 只给了三条控制指令）。所以 hgemm_wgmma 只能用 n16 铺 8 次覆盖 N=128，
A tile 每个 K 段要从共享内存重读 8 遍而不是 1 遍，宽 N wgmma 的带宽收益被吃掉一部分。
这个上限是编译器侧 ZIR 编码的历史遗留（ZIR 的 `outputs_len` 已是 u7），细节和上游
补丁建议见 `docs/upstream-asm-output-limit.md`。

因此对 wgmma 轮的性能预期要下调：在 15 输出上限解除前，不要按 70%+ 峰值来预期。

1. **描述符 + core-matrix 布局一次写对。** 这不是运气，是因为没有猜——位域和 canonical

## wgmma 流水线 A/B（2026-09-21，H20，v0.0.8-alpha）

同一次 pod 运行，shape 完全相同（64×128 tile、单 warpgroup、每段 8 条 `m64n16k16`），
唯一差异是流水线深度。

```
hgemm_wgmma   (2 级, wait_group 0)  1.711 ms  80347 GFLOPS  54.3%  max err 0
hgemm_wgmma2  (3 级, wait_group 1)  1.593 ms  86284 GFLOPS  58.3%  max err 0
```

**+4.0pp / 1.074x。对 mma.sync 基线累计 1.60x。**

> **订正（2026-09-21，见本文档末尾）**：这 +4.0pp **不是流水线的功劳**。`hgemm_wgmma2`
> 相对 `hgemm_wgmma` 同时换掉了 `cur: u1` 开关，消除了一个 1 字节的循环内溢出。
> 单独去掉那个溢出后，2 级流水的 `hgemm_wgmma` 也达到 58.3%，与 3 级版持平。
> 三级流水 + `wait_group 1` 的真实收益是 **−0.0pp**。下面「流水线不是主瓶颈」的
> 结论方向是对的，但它比我当时以为的还要彻底：排空 tensor core 的代价测不出来。

### 结论：流水线不是主瓶颈

赛前我把预期分成三档：≥65% 说明瓶颈在流水线、≈56% 说明 n16 是墙、≤v3 说明多一级不值。
实际落在 58.3%，偏向第二档——**排空 tensor core 确实在浪费，但只值 4pp，剩下的 41.7pp
不是它**。所以「先测便宜的那个」这个顺序是对的：如果先去打编译器补丁，我们会带着一个
本来就有 4pp 水分的基线去测上限的代价。

### 剩下 41.7pp 在哪：两个候选，算不出来

候选一，**n16 的 shape 代价**。每 K 段的共享内存操作数流量：

| shape | 每段读取 | flops / 共享内存字节 |
| --- | --- | --- |
| 8 × m64n16k16（现状） | 20480 B | 12.8 |
| 1 × m64n128k16（CUTLASS 用的） | 6144 B | 42.7 |

A tile 被重读 8 遍，操作数流量是 **3.3 倍**。

候选二，**全局流量**。每 block 读 1.5 MB，2048 个 block 共 3.22 GB，
按 1.593 ms 算是 **2.02 TB/s**，占 H20 HBM 标称 ~4 TB/s 的 51%（L2 会吸收一部分，
所以真实 DRAM 低于此值，但 L2 侧的需求就是这个量级）。M=64 复用面窄是根因。

**这两个我用规格书算不出谁是主因**——共享内存操作数带宽和 L2 带宽的有效值都不是
能从 spec 推准的数。继续拍脑袋不如上 profiler。

### 下一步应该是 ncu，不是补丁

```
ncu --set full -k regex:hgemmWgmma2 \
    ./zoxide bench kernels/hgemm_wgmma2.ptx --n 2048 --iters 1 --arch sm_90a
```

两个指标直接分流：

- `sm__pipe_tensor_op_hmma_cycles_active.avg.pct_of_peak_sustained_active` —— tensor
  管线利用率。若已经很高而吞吐上不去，瓶颈在喂数据（指向 n16）
- `gpu__dram_throughput.avg.pct_of_peak_sustained_elapsed` —— 若接近饱和，
  先做 M=128/双 warpgroup（流量降到约 2 GB），shape 上限反而次要

没有 ncu 的话，次便宜的判别器是直接写 M=128 双 warpgroup 版：它不依赖上游，
且结果同样能分流——大涨说明受制于流量，微涨说明 n16 是墙。

### 另外两笔

- **swizzle 撤销**：上一轮把它和三级缓冲并列是不严谨的。core matrix 是 128 字节连续，
  共享内存 32 banks × 4B = 128 字节一轮，读一个 core matrix 已经完整跨遍所有 bank
  一次，没有冲突可消。swizzle 模式是给保持宽行距的布局（TMA 产出那种）用的。
- PTX 层面两个副产品：`kt % 3` 被强度削减成轮转计数器（无 div/rem）；换掉 `cur: u1`
  开关后，`hgemm_mma2` 和 `hgemm_wgmma` 里那个每轮读写的 1 字节 `__local_depot` 消失了。

## L2 边界 sweep：流量假设被排除（2026-09-21，H20）

ncu 在 pod 上不可用（`ERR_NVGPUCTRPERM`，NVIDIA 默认把性能计数器限制给 admin，
解法是节点级的：`NVreg_RestrictProfilingToAdminUsers=0` + 重载模块，或 pod 加
`CAP_SYS_ADMIN`）。改用不需要计数器的替代实验：变 n 让 A+B 走过 L2 边界。

`hgemm_wgmma2`，设备自报 **78 SMs / 60 MB L2 / 228 KB shared per SM**：

| n | blocks | waves | A+B vs L2 | GFLOPS | 峰值 |
| --- | --- | --- | --- | --- | --- |
| 2048 | 512 | 0.55 | 16 MB，装得下 | 77830 | 52.6% |
| 3072 | 1152 | 1.23 | 36 MB，装得下 | 85663 | 57.9% |
| 4096 | 2048 | 2.19 | 64 MB，**装不下** | 86305 | 58.3% |
| 6144 | 4608 | 4.92 | 144 MB，装不下 | 85899 | 58.0% |
| 8192 | 8192 | 8.75 | 256 MB，装不下 | 85577 | 57.8% |

全部 PASS，max err 0。

### 结论：不受全局流量限制

跨过 L2 边界完全没有台阶：57.9%（装得下）→ 58.3%（装不下）→ 58.0% → 57.8%。
装不下 L2 的 n=4096 反而是最快的。如果受流量限制，这里必须出现下滑。

而且实验的偏差方向是**不利于**这个结论的：小 n 的序幕/收尾摊到更少 K 段上（128 vs 256），
本该让小 n 更快看起来更慢。即便如此也没有观察到台阶，所以排除是稳的。

n=2048 的凹陷有独立解释，不是流量：共享内存 18 KB/block 限制下每 SM 可驻留
228/18 = 12 个 block，全 GPU 936 个槽位，而 n=2048 只产生 512 个 block ——
**0.55 个 wave，GPU 根本没填满**。

另外 global reads 在所有尺寸上恒定在 2.01–2.02 TB/s。这个恒定性是**结果不是原因**：
计算速率被钉住了，取数速率跟着钉住。

### 顺带排除第三个假设

上面那个 occupancy 计算还顺手回答了一个我此前没明确列出的候选——「tensor core 缺少
独立工作可做」。每 SM 驻留 12 个 block 就是 **12 条独立的 wgmma 流**，线程占用
1536/2048 = 75%。并发不是瓶颈。

### 四个假设，三个已排除

| 假设 | 状态 |
| --- | --- |
| 流水线排空 tensor core | 已排除 —— 修好只值 4pp（v0.0.7 → v0.0.8） |
| 全局流量 / DRAM 带宽 | 已排除 —— 跨 L2 边界持平 |
| warpgroup 并发不足 | 已排除 —— 每 SM 12 条独立流、75% occupancy |
| **n16 单指令 tensor core 效率** | **剩下的唯一候选** |

必须说清这是**排除法得出的归因，不是直接测量**。要确证只有一条路：真的编出
`m64n64k16` 跑一遍，而那需要打补丁的编译器。

### 撤销一条建议

M=128 / 双 warpgroup 此前是按「降低全局流量」立项的。流量既已排除，这个理由不成立了，
应当撤销。它也不能通过提高并发来救场（并发同样已排除）。更根本的是：

**3.3 倍的操作数流量比例对 tile 形状不变**。放宽 M 或 N 只改变有多少 block 在跑，
不改变每条 wgmma 重读 A 多少次；只有**单条指令的 N 变宽**才改变它。所以在
15 输出上限解除之前，tile 层面没有可动的东西。

编译器补丁至此同时是**测量工具**和**很可能的修复手段**。我此前担心的循环
（代价要靠补丁才能量化、补丁的说服力要靠代价）已经被这次 sweep 解开：
不需要先知道代价就有充分理由去打补丁了。

## wgmma RS：A 进寄存器（2026-09-21，H20，v0.0.9-alpha）

同一次 pod 运行，三个变体 shape 完全相同（64×128 tile、单 warpgroup、每段 8 条
`m64n16k16`），差异只在操作数来源与流水线深度：

```
hgemm_wgmma   SS，2 级流水          80241 GFLOPS  54.2%  max err 0
hgemm_wgmma2  SS，3 级流水          86279 GFLOPS  58.3%  max err 0
hgemm_wgmma3  A 进寄存器（RS），3 级  95175 GFLOPS  64.3%  max err 0
```

**+6.0pp（1.103x），对 mma.sync 基线累计 1.77x。**

### 我上一轮的归因是错的，这里纠正

上一轮我把剩余 41.7pp 全部归给「n16 shape」，并断言：

> 3.3 倍的操作数流量比例对 tile 形状不变……只有单条指令的 N 变宽才改变它。
> 所以在 15 输出上限解除之前，tile 层面没有可动的东西。

**这是错的。** 我整个推理都待在 wgmma 的 SS 形态里（A、B 都从共享内存取），
漏掉了 RS 形态——A 从寄存器取，累加器仍是 8 个，落在 15 输出限制内。

| 形态 | 每 K 段共享内存读取 | flops/byte |
| --- | --- | --- |
| SS n16 | 8 × (A 2048 + B 512) = 20480 B | 12.8 |
| **RS n16（本轮）** | A 2048 + 8 × 512 = **6144 B** | **42.7** |
| SS n128（需补丁） | A 2048 + B 4096 = 6144 B | 42.7 |

A 每段只读一次、之后从寄存器喂给全部 8 条 wgmma，读取量与单条 `m64n128k16` 完全相同。
实测 +6.0pp 说明操作数饥饿是真实成本，且**在原版 Zig 里就能解决**。

教训是：用排除法收敛到「shape」之后，我把「shape」当成了一个不可分解的原因。
它其实至少含两个可分的成分——操作数流量和单指令成本——而前者有第二条解法。
排除法能指出方向，不能代替对机制的分解。

### 但这也让补丁的理由变强了

操作数流量现已与 n128 持平（42.7 flops/byte），**却仍距峰值 35.7pp**。
所以剩下的成本已经不是喂数据，而是单指令层面的：8 条指令做 1 条的事。
要测这一项只有把 N 变宽，而那正是 15 输出上限挡住的。

补丁此前的理由是「量化一个我们猜是主因的东西」，现在变成「操作数流量已被消掉，
剩余差距只能是单指令成本，而我们被禁止测量它」。这是个强得多的陈述。

### PTX 层面被揪出来的两个 bug

两个都只在读生成的 PTX 时才暴露，源码上看不出来：

1. `afrag[kt % 2]` 的运行时下标把寄存器数组赶进了 local memory——每轮 20 条
   `st.local`，比想省掉的共享内存重读更糟。改成两个具名局部变量 + block-uniform 分支。
2. 即便如此，寄存器分配器认为每个 fragment 在其最后一条 wgmma 之后即死亡，
   把物理寄存器回收给下一段，**悄悄把源码里表达的双缓冲合并掉了**——而此时上一段的
   wgmma 仍在异步读它。用 CUTLASS 的 `warpgroup_fence_operand` 手法（空 asm 带 `+r`
   操作数）把两组钉活到循环回边之外。

最终 PTX：两组不相交的 4 寄存器各驱动 8 条 wgmma、2 条 ldmatrix 对 16 条 wgmma、0 spill。

### 顺带

A 不再作为描述符操作数，于是不需要 core-matrix packing，改回普通 `[64][16]` f16
（32 B 行距）——正是 ldmatrix 想要的布局。CUTLASS 的 `ALayout_64x16` 解出来就是
`mma.sync m16n8k16` 的 A fragment 布局按 warp 铺各自的 16 行，即一条 `ldmatrix.x4`，
所以 `hgemm_mma2` 的寻址可以原样复用。

## 订正：occupancy 是 25% 不是 75%，寄存器才是约束（2026-09-21，H20）

绑上 `cuOccupancyMaxActiveBlocksPerMultiprocessor` 之后，驱动给出的真实数字：

```
kernel: 98 regs/thread, 18432 B static shared,
        4 blocks/SM at 128 threads (512/2048 threads = 25% occupancy, 78 SMs)
```

**我此前手算的 12 blocks/SM 是错的。** 算法本身没错，但算的是错的限制：

| 约束 | 计算 | 结果 |
| --- | --- | --- |
| 共享内存（我算的） | 228 KB ÷ 18 KB | 12 blocks |
| **寄存器（真正的约束）** | 98 → 按 8 取整 104 × 128 线程 = 13312；65536 ÷ 13312 | **4 blocks** |

寄存器模型与驱动答案精确吻合（4.92 → 4），说明这个解释是对的而不是巧合。

### 后果：一个被排除的假设必须撤回

我在「四个候选，三个已排除」那张表里写过：

> warpgroup 并发不足 —— 已排除，每 SM 12 条独立流、75% occupancy

**这条排除建立在错数据上。** 真实是**每 SM 4 条独立 wgmma 流、25% 线程占用**。
12 条流 / 75% 说「并发充足」是有说服力的；4 条流 / 25% 完全没有这种说服力。
所以这个假设回到待定状态。

修正后的表：

| 假设 | 状态 |
| --- | --- |
| 流水线排空 tensor core | 已排除 —— 修好值 4.1pp |
| 全局流量 / DRAM 带宽 | 已排除 —— 跨 L2 边界持平 |
| **warpgroup 并发不足** | **撤回排除** —— 依据的 occupancy 数字错了；真实 4 blocks/SM、25% |
| 共享内存操作数饥饿 | 已排除 —— 修好值 6.0pp |
| n16 单指令 tensor core 效率 | 待定 |

需要说明的是，低 occupancy 对 wgmma 类 kernel **不一定是病**：CUTLASS 的 SM90 kernel
同样用少量、重寄存器的 warpgroup（配合 `setmaxnreg` 在生产者/消费者之间再分配），
线程占用也在 20% 上下。所以 25% 可能是正常的，也可能是瓶颈——这需要测，不能靠论证。

### 下一个实验只差 2 个寄存器

```
4 blocks/SM  需要 <= 128 regs/thread   <- 现在 98（取整 104）
5 blocks/SM  需要 <= 102 -> 取整 <= 96  还需省 2 个
6 blocks/SM  需要 <= 85  -> 取整 <= 80  还需省 18 个
```

98 → 96 就能多拿一个 block，occupancy 从 25% 到 31%。而这不需要改 kernel：

```
./zoxide bench kernels/hgemm_wgmma3.ptx --n 4096 --iters 10 --arch sm_90a --maxrregcount 96
```

本轮为此给 `bench` / `run` 加了 `--maxrregcount` 直通 ptxas。代价是 ptxas 会把
溢出的部分挪到 local memory；2 个寄存器的溢出换 +25% occupancy 是否划算无法预测，
所以做成了开关而不是默认值。bench 的 spill 警告会直接显示代价。

98 个寄存器里 64 个是累加器（8 tile × 8），这部分动不了；剩下 34 个里有 8 个是
A fragment 双缓冲。所以真要往下压，`--maxrregcount` 比手工省寄存器更现实。

### 方法上的教训（第二次同类）

上一轮的教训是「排除法指方向，不能代替对机制的分解」。这一轮是同一件事的另一面：
**排除一个假设之前，先确认用来排除它的数字是测出来的而不是推出来的。**
共享内存那个除法看起来很硬——单位对得上、数量级合理——但它默默忽略了寄存器这个
维度。驱动里那个 API 一直都在，我只是没绑。

## 寄存器上限扫描：occupancy 不是约束（2026-09-21，H20）

`hgemm_wgmma3`，n=4096，`--maxrregcount` 逐档收紧：

| cap | 实际 regs | blocks/SM | occupancy | GFLOPS | 峰值 | 相对 | 溢出 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 无 | 98 | 4 | 25% | 95234 | 64.3% | 1.00x | 0 |
| 104 | 100 | 4 | 25% | 95565 | 64.6% | 1.00x | 0 |
| 96 | 94 | **5** | **31%** | 92186 | 62.3% | **0.97x** | 0 |
| 88 | 88 | 5 | 31% | 52234 | 35.3% | 0.55x | 64 B |
| 80 | 80 | 6 | 38% | 37359 | 25.2% | 0.39x | 128 B |
| 72 | 72 | 7 | 44% | 27760 | 18.8% | 0.29x | 192 B |

全部 PASS，max err 0——包括重度溢出那几档，说明溢出只伤性能不伤正确性。

### 结论一：并发假设这次被真正排除了

`cap 96` 是关键一行：**零溢出**，occupancy 从 25% 提到 31%，吞吐反而**掉了 3%**。

所以「warpgroup 并发不足」不成立，而且这次是测出来的而不是推出来的——上一轮我拿
一个算错的 occupancy 去排除它，现在是拿实测的「提高 occupancy 会变慢」去排除它。
4 个 block 已经够掩藏延迟；再多的 block 只是争抢同一个 tensor core 和共享内存带宽，
不提供有用的并行度。这也印证了 CUTLASS 在 SM90 上走「少量重寄存器 warpgroup」
（~20% 占用）的选择不是妥协，而是这类 kernel 的正确形态。

`cap 104` 那行比无上限快 0.3%（95565 vs 95234）。**这在噪声内，不当作结论**——
ptxas 在有上限时选了 100 个寄存器而不是 98，调度略有不同，但 0.3% 不足以支撑任何说法。

### 结论二：溢出的代价被量化了，而且极大

| 溢出 | 折合寄存器 | 吞吐 |
| --- | --- | --- |
| 64 B/thread | 16 个 | **0.55x** |
| 128 B/thread | 32 个 | 0.39x |
| 192 B/thread | 48 个 | 0.29x |

溢出 16 个寄存器就砍掉 45% 吞吐。这回过头验证了一件事：写 `hgemm_wgmma3` 时，
`afrag[kt % 2]` 的运行时下标曾产生每轮 20 条 `st.local`，我是靠 grep 生成的 PTX
才发现的（源码上双缓冲写得完全正确）。按这张表，那个 bug 的代价大致等于
**整个 wgmma 路线的全部收益**——它会把 64.3% 打回 35% 上下，比 mma.sync 基线还低。

这也是为什么 CI 里那条「`hgemm_wgmma3.ptx` 不许出现 `st.local`」的守卫值得存在，
以及为什么 bench 的 spill 警告不是装饰。

### 修正后的候选表

| 假设 | 状态 |
| --- | --- |
| 流水线排空 tensor core | 已排除 —— 修好值 4.1pp（v0.0.8） |
| 全局流量 / DRAM 带宽 | 已排除 —— 跨 L2 边界持平 |
| 共享内存操作数饥饿 | 已排除 —— 修好值 6.0pp（v0.0.9） |
| warpgroup 并发 / occupancy | **已排除（实测）** —— 零溢出下提高 occupancy 反而 0.97x |
| **n16 单指令 tensor core 效率** | **剩下的唯一候选** |

寄存器这个维度就此关闭：98 regs / 4 blocks / 25% 已经是最优点，往两边都更差。

回到 n16 这个结论跟 v0.0.9 时一样，但性质不同了——那时它是「其他都排除了所以只剩它」，
其中一条排除还建立在错数字上；现在四条排除全部有实测支撑。测它仍然只有一条路：
把 N 变宽，而那需要打补丁的编译器。

### hgemm 五个 kernel：数字不变，结果精确

签名从字节指针（`[*]const u8` / `hgemm_mma` 的 `u16`）改为 `[*]const f16` 之后：

| kernel | GFLOPS | 峰值 | 对比 v0.0.10 |
| --- | --- | --- | --- |
| hgemm_mma | 36782 | 24.9% | 36800 |
| hgemm_mma2 | 53899 | 36.4% | 53839 |
| hgemm_wgmma | 80426 | 54.3% | 80241 |
| hgemm_wgmma2 | 86390 | 58.4% | 86279 |
| hgemm_wgmma3 | **95262** | **64.4%** | 95175 |

全部 PASS，max err 0。核心 PTX 指令计数改动前后一致这个证据成立了。

顺带暴露一件此前看不见的事：`hgemm_mma2` 和 `hgemm_wgmma` 报 **8 B/thread 溢出**。
这就是我早先在 PTX 里注意到的那个 1 字节 `__local_depot0`（`cur: u1` 缓冲开关），

### host API 首次真机运行：失败，原因正是它该抓的那个 bug

```
device: NVIDIA H20 (78 SMs, 60 MB L2)
error: CudaCall
```

`tests/downstream` 的 PTX 入口是 `kernel_$_scale`（来自 `kernel.zig`），
而 `main.zig` 查的是 `downstream_kernel_$_scale`（构建产物名）。
`cuModuleGetFunction` 找不到 → 失败。

**这个 bug 我在脚手架里修过，却没修 `tests/downstream` 本身**——而脚手架正是照它建模的。
CI 里那条「入口点 == 查找符号」的断言我也只加给了脚手架。根因是：
**在没有 GPU 的机器上，这个错误完全无法被检测**——包能编译、能链接、能优雅退化，
一切看起来正常。这是「从未在真硬件上跑过」这笔债的直接后果。

三处修补：

1. `tests/downstream` 的对象名改为 `kernel`，与 `kernel.zig` 一致，三个名字统一。
2. CI 的入口点断言扩展到 `tests/downstream`，不只是脚手架。
3. `error: CudaCall` 本身是个问题——它没告任何信息。`cuModuleGetFunction` 返回
   `CUDA_ERROR_NOT_FOUND`(500)，现在映射为独立的 `error.KernelNotFound`，消息带上符号名
   和命名规则：

```
FAIL: KernelNotFound: kernel 'downstream_kernel_$_scale' not found in module;
the PTX symbol is <root source file stem>_$_<decl>, e.g. kernel_$_scale for
kernel.zig — not the build artifact's name
```

downstream 和脚手架模板现在都把 `drv.lastError()` 打出来，而不是让错误裸着冒出去。

### 教训

这个符号命名规则我已经踩过两次：第一次是 `symbol()` 的文档写成了「构建产物名」，
脚手架照抄；这次是 `tests/downstream` 没跟着一起修。第一次我加了 CI 断言——但只加给了
新代码，没回头覆盖既有的那份。**修一个 bug 的时候要找同一模式的全部实例，而不只是发现它的那处。**

### 修补后复验：host API 首次真机全通（2026-09-21，H20）

```
device: NVIDIA H20 (78 SMs, 60 MB L2)
kernel: 10 regs/thread, 0 B shared, 8 blocks/SM at 256 threads
PASS: downstream typed launch on a stream, 1048576 elements exact
```

一趟里验证的东西：与设备共享签名的类型化 launch、non-blocking stream、
page-locked 暂存、设备侧 `0xff` 染毒（所以「什么都没写」的 kernel 不能靠留零混过）、
异步上传、流上启动、异步下载、单次 sync、以及驱动的 occupancy/resources 查询。

`8 blocks/SM at 256 threads` = 2048 线程 = 100% occupancy。这对一个 10 寄存器、
零共享内存的平凡 kernel 是应该的，顺带反证 occupancy 查询本身没问题——
`hgemm_wgmma3` 那边报 25% 是那个 kernel 的真实情况，不是 API 的错。

这条路径同时是 `zoxide new` 生成的那条，所以脚手架产出的包也确认能跑。

## 订正：v0.0.8 的「三级流水 +4.1pp」实际是那个 1 字节溢出（2026-09-21，H20）

去掉 `hgemm_mma2` / `hgemm_wgmma` 里的 `cur: u1` 开关（唯一改动）后复测：

| kernel | 改前 | 改后 | Δ | 说明 |
| --- | --- | --- | --- | --- |
| hgemm_mma | 24.9% | 24.8% | −0.0 | 无此开关，未变 |
| hgemm_mma2 | 36.4% | **36.8%** | +0.4 | 去溢出 |
| **hgemm_wgmma** | **54.3%** | **58.3%** | **+4.0** | **去溢出，2 级流水未动** |
| hgemm_wgmma2 | 58.4% | 58.3% | −0.1 | 早已无此开关 |
| hgemm_wgmma3 | 64.4% | 64.4% | −0.0 | 早已无此开关 |
| sgemm_swz | — | 42.8% FP32 | — | 未变 |

全部 PASS。

**`hgemm_wgmma`（2 级流水）现在与 `hgemm_wgmma2`（3 级流水）完全相等，都是 58.3%。**
拆解 v0.0.8 记的那 +4.1pp：

```
去 1 字节溢出        +4.0pp   (1.073x)
三级流水 + wait_group 1   -0.0pp
```

### 错在哪

`hgemm_wgmma2` 相对 `hgemm_wgmma` 同时改了两件事：流水线深度（有意），以及把
`cur: u1` 换成 `kt % stages`（无意）。我把全部差值记给了前者。

更糟的是我**当时就注意到了第二件**并写进了提交信息——「两个意外收获：`kt % 3` 被强度
削减成轮转计数器；换掉 `cur: u1` 之后那个 1 字节 `__local_depot` 消失了」——却把它
称作「意外收获」，并在同一段里宣称「shape 一字未动，所以这是一次干净的 A/B」。

**在明知改了两处的情况下称之为干净的 A/B，这是方法错误，不是运气不好。**
一次只改一个变量；如果顺带发现了第二处改动，它就是另一个实验，不是脚注。

### 连带订正

1. **候选假设表**：此前记「流水线排空 tensor core —— 已排除，修好值 4.1pp」。
   实际排空**根本不值钱**（−0.0pp）。这个假设排除得更彻底了：它从来不是因素。
   `wgmma.wait_group 0` 每段排空 tensor core，在这个 kernel 上代价测不出来。

2. **`hgemm_wgmma2` 现在是冗余的**：与 2 级版同吞吐，却多用 6 KB 共享内存
   （18 vs 12 KB）、多一级缓冲的复杂度。保留它作为技术演示，但注释已改为
   如实说明「三级流水在此 kernel 上测不出收益」。

3. **v0.0.9 的 RS +6.0pp 仍然成立**：那次比的是 wgmma2 → wgmma3，两者都无溢出。

### 一个 1 字节的 local store 值 7.3% 吞吐

这是本轮最值得记住的数字。不是 64 字节、不是累加器溢出——是循环里**一个字节**的
局部变量。驱动把它报成 8 B/thread，看起来微不足道。

结合早先的寄存器上限扫描（16 个寄存器溢出 = 0.55x），现在有了两个数据点：
Hopper 上任何进入 local memory 的循环内变量都是重大代价，不存在「小溢出」。
bench 的 spill 警告和 CI 里那条 `st.local` 守卫因此都是必需的。

### 新增：全部 kernel 的寄存器与 occupancy

| kernel | regs/thread | 共享内存 | blocks/SM | occupancy | 峰值 |
| --- | --- | --- | --- | --- | --- |
| hgemm_mma | 66 | 4 KB | 7 | 44% | 24.8% |
| hgemm_mma2 | 160 | 16 KB | 3 | 19% | 36.8% |
| hgemm_wgmma | 93 | 12 KB | 5 | 31% | 58.3% |
| hgemm_wgmma2 | 90 | 18 KB | 5 | 31% | 58.3% |
| hgemm_wgmma3 | 102 | 18 KB | 4 | 25% | **64.4%** |
| sgemm_swz | 113 | 16 KB | 4 | 25% | 42.8% (FP32) |

再次印证 occupancy 不是驱动因素：最慢的 `hgemm_mma` occupancy 最高（44%），
最快的 `hgemm_wgmma3` 最低（25%）。
