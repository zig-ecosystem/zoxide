## 发现并修复的真机 bug

atomic_counter 初版死锁：LLVM 将 `bar.sync` 复制到 `if (tid==0)` 条件分支两侧（extern 声明缺 convergent/noduplicate 属性），与 cuda-oxide 禁用 JumpThreading 同类。修复：条件初始化改为全线程无条件写；编码规则记入 README 已知问题。修复版本 v0.0.3-alpha 复验 PASS。

## FP16 tensor core 性能轮（2026-09-21，v0.0.6-alpha）

`hgemm_mma2`（128×128 tile、ldmatrix.x4/x2.trans、cp.async 双缓冲）→ **PASS，53904 GFLOPS（36.4% FP16 峰值），max err 0**（基线 hgemm_mma 36.8 TF/24.9%）。提升 +11.5pp 但未达 50% 目标。

分析：mma.sync 在 Hopper 上本就吃不满 tensor core——sm_90 的完整吞吐要 **wgmma.mma_async**（warpgroup 级指令）。

订正（2026-09-21 复查）：此前记录的「生成器已含 wgmma wrapper」不成立。`src/gen/instrinsics_asm.zig`
中 wgmma 出现 0 次；`src/gen/intrinsics.zig` 只有 `wgmma_fence` / `wgmma_commit_group` 两条控制指令，
上游 catalog 的 wgmma 条目也只有 fence / commit_group / wait_group 三条。原因是 LLVM NVVM 没有
`llvm.nvvm.wgmma.mma_async` 这个 intrinsic——mma_async 只能手写 inline asm，且需要 `sm_90a`
（LLVM predicate `hasSM90a`），不是 `sm_90`。

版本管理调整：alpha 迭代改用补丁号（v0.0.N-alpha），v0.1.0 保持唯一 stable。

## wgmma 轮：本地已就绪，待 pod 验证（2026-09-21）

新增（宿主机仅能验证到 PTX 生成，正确性/性能待 H20 pod 跑）：

- `src/wgmma.zig`：手写 `wgmma.mma_async.sync.aligned.m64n16k16.f32.f16.f16`
  + 64 位共享内存矩阵描述符编码 + fence/commit_group/wait_group 封装。描述符位域与
  core-matrix 布局依据 CUTLASS `cute`（BSD-3-Clause）`mma_sm90_desc.hpp` /
  `mma_traits_sm90_gmma.hpp`。
- `src/examples/wgmma_smoke.zig`：自检 kernel。一个 warpgroup 填 64×16 A 与 16×16 B
  的 core-matrix packed 布局，发一条 wgmma，再按闭式重算全部 1024 个累加元素逐一比对，
  把不匹配数写回 `out[tid]`。这把最容易错的「描述符 + 布局 + 累加器寄存器映射」
  从 GEMM tiling 里隔离出来单独验。输入是小整数，f16 与 f32 都精确，不匹配即真 bug。
- `src/examples/hgemm_wgmma.zig`：64×128 block tile、单 warpgroup、K=16 分段、
  cp.async 双缓冲，每段发 8 条 `m64n16k16`。
- `build.zig` 支持按 kernel 覆盖 sm 型号（wgmma 两个 kernel 走 `sm_90a`）；
  `validateArch` 接受 `sm_90a`；`pod-verify.sh` 加 `run/wgmma_smoke` 与
  `bench/hgemm_wgmma` 两项（sm_90a 不可用时记 SKIP 而非 FAIL）。

本地已确认：两个 kernel 都能编出 `.target sm_90a` 的 PTX，指令形态为
`wgmma.mma_async.sync.aligned.m64n16k16.f32.f16.f16 {8 regs}, %rd, %rd, p, 1, 1, 0, 1`，
fence/commit_group/wait_group 位置正确，共享内存 12 KB。**尚未在 GPU 上跑过，
也没有 ptxas（宿主机 macOS 无 CUDA 工具链），所以布局正确性与性能都还是未验证状态。**

### 为什么是 n16 而不是 n128

`m64nNk16` 每线程需要 N/2 个累加器寄存器，且每个都必须是 inline asm 的 output 操作数。
Zig AstGen 把 asm output 上限硬编码在 15（`lib/std/zig/AstGen.zig`，"too many asm outputs"），
本地实测 15 个能编过、16 个报错。于是：

| shape | 累加器寄存器 | Zig 能否表达 |
| --- | --- | --- |
| `m64n16k16` | 8 | 能 |
| `m64n32k16` | 16 | 不能，正好超 1 个 |
| `m64n64k16` | 32 | 不能 |
| `m64n128k16` | 64 | 不能 |

不能靠拆分 asm 绕开——一条 wgmma 的累加器必须在同一个操作数列表里；也没有 intrinsic
可退（NVVM 只给了三条控制指令）。所以 hgemm_wgmma 只能用 n16 铺 8 次覆盖 N=128，
A tile 每个 K 段要从共享内存重读 8 遍而不是 1 遍，宽 N wgmma 的带宽收益被吃掉一部分。
这个上限是编译器侧 ZIR 编码的历史遗留（ZIR 的 `outputs_len` 已是 u7），细节和上游
补丁建议见 `docs/upstream-asm-output-limit.md`。

因此对 wgmma 轮的性能预期要下调：在 15 输出上限解除前，不要按 70%+ 峰值来预期。

| kernel | 指令 | GFLOPS | FP16 峰值占比 | 误差 |
| --- | --- | --- | --- | --- |
| hgemm_mma | mma.sync m16n8k16 | 36800 | 24.9% | 0 |

wgmma 对 mma.sync 的加速比 **1.49x**，+17.9pp。上一轮 mma.sync 没摸到的 50% 目标，
这轮在带着 n16 手铐（见下）的情况下已经越过。

两点值得记下：

1. **描述符 + core-matrix 布局一次写对。** 这不是运气，是因为没有猜——位域和 canonical
   layout 是从 CUTLASS `cute` 的 `mma_sm90_desc.hpp` 与 `mma_traits_sm90_gmma.hpp`
   （BSD-3-Clause）推出来的，累加器寄存器到 (m,n) 的映射来自 `CLayout_64xN`。
   `wgmma_smoke` 这个自检 kernel 也起到了预期作用：它把布局层从 GEMM tiling 里隔离出来，
   如果真错了，能直接定位到是描述符、packing 还是寄存器映射，而不是从 GEMM 的误差反推。

2. **54.3% 是带着 15 输出上限的成绩。** 受 Zig AstGen 的 asm output ≤15 限制，shape 只能用
   `m64n16k16`（8 个累加器寄存器），`m64n32k16`（16 个）正好超 1 个。所以 N=128 要用 n16
   铺 8 次，A tile 每个 K 段从共享内存重读 8 遍而非 1 遍。CUTLASS 参考实现用的是
   `m64n128k16`。上限解除到 32 就能用 `m64n64k16`，还剩多少空间未测——这是下一轮该量化的。
   细节见 `docs/upstream-asm-output-limit.md`。

## wgmma 流水线 A/B（2026-09-21，H20，v0.0.8-alpha）

同一次 pod 运行，shape 完全相同（64×128 tile、单 warpgroup、每段 8 条 `m64n16k16`），
唯一差异是流水线深度。

```
hgemm_wgmma   (2 级, wait_group 0)  1.711 ms  80347 GFLOPS  54.3%  max err 0
hgemm_wgmma2  (3 级, wait_group 1)  1.593 ms  86284 GFLOPS  58.3%  max err 0
```

**+4.0pp / 1.074x。对 mma.sync 基线累计 1.60x。**

### 结论：流水线不是主瓶颈

赛前我把预期分成三档：≥65% 说明瓶颈在流水线、≈56% 说明 n16 是墙、≤v3 说明多一级不值。
实际落在 58.3%，偏向第二档——**排空 tensor core 确实在浪费，但只值 4pp，剩下的 41.7pp
不是它**。所以「先测便宜的那个」这个顺序是对的：如果先去打编译器补丁，我们会带着一个
本来就有 4pp 水分的基线去测上限的代价。

### 剩下 41.7pp 在哪：两个候选，算不出来

候选一，**n16 的 shape 代价**。每 K 段的共享内存操作数流量：

| shape | 每段读取 | flops / 共享内存字节 |
| --- | --- | --- |
| 8 × m64n16k16（现状） | 20480 B | 12.8 |
| 1 × m64n128k16（CUTLASS 用的） | 6144 B | 42.7 |

A tile 被重读 8 遍，操作数流量是 **3.3 倍**。

候选二，**全局流量**。每 block 读 1.5 MB，2048 个 block 共 3.22 GB，
按 1.593 ms 算是 **2.02 TB/s**，占 H20 HBM 标称 ~4 TB/s 的 51%（L2 会吸收一部分，
所以真实 DRAM 低于此值，但 L2 侧的需求就是这个量级）。M=64 复用面窄是根因。

**这两个我用规格书算不出谁是主因**——共享内存操作数带宽和 L2 带宽的有效值都不是
能从 spec 推准的数。继续拍脑袋不如上 profiler。

### 下一步应该是 ncu，不是补丁

```
ncu --set full -k regex:hgemmWgmma2 \
    ./zoxide bench kernels/hgemm_wgmma2.ptx --n 2048 --iters 1 --arch sm_90a
```

两个指标直接分流：

- `sm__pipe_tensor_op_hmma_cycles_active.avg.pct_of_peak_sustained_active` —— tensor
  管线利用率。若已经很高而吞吐上不去，瓶颈在喂数据（指向 n16）
- `gpu__dram_throughput.avg.pct_of_peak_sustained_elapsed` —— 若接近饱和，
  先做 M=128/双 warpgroup（流量降到约 2 GB），shape 上限反而次要

没有 ncu 的话，次便宜的判别器是直接写 M=128 双 warpgroup 版：它不依赖上游，
且结果同样能分流——大涨说明受制于流量，微涨说明 n16 是墙。

### 另外两笔

- **swizzle 撤销**：上一轮把它和三级缓冲并列是不严谨的。core matrix 是 128 字节连续，
  共享内存 32 banks × 4B = 128 字节一轮，读一个 core matrix 已经完整跨遍所有 bank
  一次，没有冲突可消。swizzle 模式是给保持宽行距的布局（TMA 产出那种）用的。
- PTX 层面两个副产品：`kt % 3` 被强度削减成轮转计数器（无 div/rem）；换掉 `cur: u1`
  开关后，`hgemm_mma2` 和 `hgemm_wgmma` 里那个每轮读写的 1 字节 `__local_depot` 消失了。
